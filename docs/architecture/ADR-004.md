# ADR-004: Composite Geocoder & Two-Level Caching Strategy

## Status
**ACCEPTED** (Date: 2026-08-06)

## Context
Production astrology engine deployments require resilient, high-speed geocoding resolution and efficient response caching. Relying on a single third-party web geocoding service introduces latency bottlenecks and single-point-of-failure vulnerabilities.

## Decision
We decide to adopt:
1. **Composite Geocoder Chain**:
   - Order of execution: `OfflineDatabase` -> `GeoNames` -> `Nominatim` -> `GoogleMaps`.
   - The engine attempts each provider in sequence. If a provider throws an exception or times out, the composite wrapper logs a warning and falls back to the next provider.
2. **Two-Level Caching (`L1` Memory + `L2` Redis)**:
   - `L1 Memory Cache`: Instant in-memory dictionary lookup ($<0.001\text{ ms}$).
   - `L2 Redis Cache`: Distributed persistent cache shared across engine instances.
   - Read strategy: L1 Hit -> Return immediately. L1 Miss -> Check L2. L2 Hit -> Populate L1 and Return. L2 Miss -> Compute & Store in L1 and L2.
3. **Resilience & Timeouts**:
   - All network providers configure exponential backoff retries and strict HTTP socket timeouts (default 3.0s).

## Consequences

### Positive
- **High Availability**: Fallback chain guarantees location resolution even if external APIs are degraded or unconfigured.
- **Microsecond Latency**: L1/L2 caching reduces repeated location resolution runtime to $<0.01\text{ ms}$.
- **Backward Compatibility**: API endpoints maintain identical response payloads.
